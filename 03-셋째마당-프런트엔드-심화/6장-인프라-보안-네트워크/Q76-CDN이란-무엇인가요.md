# Q76. CDN은 무엇이며, 프런트엔드 앱 성능 개선에 어떻게 기여하나요?

### CDN이란?

- 웹의 물리적 한계
    - 어떤 웹 사이트의 원본 서버(origin server)가 서울에 있다고 가정해보자.
    - 데이터는 수많은 네트워크 장비를 거치며 지연(latency)이 발생한다.
    - 사용자가 서울에 산다면 서버와의 거리가 가까움
        
        → 웹 사이트의 이미지, 동영상, 코드 파일을 매우 빠르게 내려받을 수 있음.
        
    - 사용자가 뉴욕에 산다면 속도가 느려질 수밖에 없음
- **CDN(Content Delivery Network)**: 이러한 물리적 한계를 극복하기 위해 등장한 것이 바로 콘텐츠 전송 네트워크.
    - **원본 서버의 콘텐츠를 미리 “복사”**하여 전 세계 곳곳에 흩어져 있는 **캐시 서버** 또는 **에지 서버**에 저장해 두는 거대한 **네트워크 시스템**.
    
    !image.png
    
- CDN의 작동 방식
    - 서울에 본사를 두고, 전 세계 주요 도시에 프랜차이즈 지점을 내서 운영하는 거에 비유해보자.
    1. 가장 가까운 지점으로 연결
        - 뉴욕의 고객이 주문하면 **가장 가까운 뉴욕 지점**(CDN 캐시 서버)이 주문을 바로 접수.
    2. 빠른 콘텐츠 제공
        - 뉴욕 지점은 이미 보관 중인 레시피와 재료(캐시된 콘텐츠)로 음식을 만들어 고객에게 즉시 제공.
    3. 원본 서버 부하 감소
        - 전 세계의 모든 주문을 서울 본사가 감당할 필요 없음.
        - 각 지역 지점이 알아서 처리하므로 원본 서버는 과부하 없이 안정적인 운영 가능.
- 즉, 사용자가 웹 사이트에 접속 → CDN이 사용자와 가장 가까운 위치의 캐시 서버로 연결하여 콘텐츠 전송 → 빠른 속도 체감 가능

### CDN의 장점

- **로딩 속도 대폭 개선**
    - 사용자와 서버 간의 **물리적 거리 단축** → **데이터 전송 시간 최소화**
    - 이미지나 동영상 같은 무거운 리소스의 로딩 속도를 높여줌
- **원본 서버 부하 감소**
    - 전 세계 사용자의 트래픽이 CDN의 캐시 서버들로 분산됨
    - 원본 서버는 트래픽 폭주로 인한 장애 위험에서 벗어나 동적인 데이터 처리나 API 요청과 같은 핵심적인 역할에만 집중 가능
- **높은 안정성과 가용성**
    - 특정 지역의 CDN 캐시 서버에 문제가 생겨도 **다른 지역의 서버가 요청을 이어받아 처리 가능.**
    - 원본 서버가 다운되어도 CDN에 캐시된 콘텐츠는 게속 사용자에게 제공될 수 있음
- **비용 절감**
    - 트래픽 비용(원본 서버가 주고받는 데이터 양)이 크게 줄어듦.

### CDN 고려 사항

- **캐시 관리**
    - 예: 웹 사이트의 로고 이미지를 새 버전으로 업데이트한 상황.
    - 원본 서버의 파일은 바뀌었지만 전 세계에 분산된 CDN 캐시 서버에는 여전히 이전 로고 이미지가 남아 있을 수 있다.
    - **캐시 무효화**: 로고 파일이 변경되었다는 것을 CDN에 알려 주고 **기존에 저장된 파일을 삭제**한 뒤 **원본 서버에서 새로운 파일을 다시 가져가도록** 해야 함.
    - 캐시 무효화를 어떤 식으로 관리할지 미리 전략을 세워두는 것 중요.
- **비용 문제**
    - CDN은 **사용한 트래픽의 양이나 요청 횟수**에 따라 **비용을 부과**함.
    - 서비스의 트래픽 규모를 예측하고 예상 비용이 합리적인지 미리 검토
    - 주요 CDN 서비스(Amazon CloudFront, Cloudflare, Akamai)는 무료 플랜이나 저렴한 스타터 플랜 제공.
- **동적 콘텐츠 처리**
    - CDN은 주로 **정적 콘텐츠를 제공하는 데 최적화**되어 있음.
        
        → 이미지, CSS, 자바스크립트 파일처럼 자주 변경되지 않는 콘텐츠는 CDN에 캐싱하면 큰 효과를 볼 수 있음.
        
    - 반면 **동적 콘텐츠는 캐싱해서는 안 됨.**
        - 데이터의 내용이 시시각각 달라지므로 애초에 캐시 잘체를 할 수 없음.
    - 어떤 콘텐츠를 캐싱할지, 어떤 요청은 캐싱하지 않고 바로 원본 서버로 전달할지를 명확히 구분해야 함.

### 모의 면접

1. CDN이 웹 앱의 성능을 개선하는 핵심 원리와 장점은 무엇인가요?
    
    > CDN은 원본 서버의 콘텐츠를 전 세계 에지 서버에 캐싱해 두고, 사용자를 가장 가까운 서버로 연결합니다. 물리적 거리가 짧아지니 지연 시간이 줄어 로딩 속도가 빨라집니다.
    장점은 로딩 속도 개선, 트래픽 분산으로 인한 원본 서버 부하 감소, 일부 서버 장애에도 서비스가 유지되는 높은 가용성, 원본 서버 트래픽 비용 절감입니다.
    > 
2. CDN 사용 시 반드시 고려해야 할 주요 사항은 무엇인가요?
    
    > 첫째, 캐시 무효화 전략입니다. 원본이 바뀌어도 에지에는 이전 파일이 남을 수 있어서, 무효화 요청을 보내거나 빌드 시 파일명에 해시를 붙여 변경된 파일이 새 파일로 인식되게 합니다.
    둘째, 동적 콘텐츠 구분입니다. 사용자별 데이터를 잘못 캐싱하면 다른 사용자에게 노출될 수 있으므로, Cache-Control 헤더 등으로 캐싱 대상을 명확히 나눠야 합니다.
    셋째, 트래픽과 요청 수에 따라 과금되므로 예상 비용을 미리 검토해야 합니다.
    > 

### 추가 공부

- 에지 서버랑 캐시 서버는 다른 것인가?
    - **에지 서버**: **위치**를 강조한 이름. 네트워크의 가장자리(edge), 즉 사용자랑 가장 가까운 곳에 있는 서버라는 뜻.
    - **캐시 서버**: **역할**을 강조한 이름. 원본의 복사본을 저장해 두고 대신 내주는 서버라는 뜻.
    - CDN의 서버는 사용자 가까이 있으면서(에지) 콘텐츠를 저장해 두니까(캐시) 둘 다 맞는 표현이라 섞어서 씀.
